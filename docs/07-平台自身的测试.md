# test-platform · 文档07 平台自身的测试

> 一句话："测平台的平台也要被测"——38 条 pytest 分三层（断言引擎纯单测 / 执行引擎 mock 单测 / Web+API 端到端），集成测试用标记隔离，不依赖 demo-mall 也能全量跑。

## 1. 在整个平台中的位置

tests/ 是平台**质量的闭环**：它测的对象就是平台本身（吃自己的狗粮），分层方式与"如何测一个被测系统"完全同构。

```mermaid
flowchart TB
    subgraph TESTS["tests/ 三层"]
        T1["test_assert_engine.py（9 条）<br/>纯单测：内存 Response<br/>三层断言矩阵"]
        T2["test_runner.py（8+2 条）<br/>单测：monkeypatch _send<br/>集成：真实 demo-mall"]
        T3["test_web_api.py（21+1 条）<br/>test client 端到端<br/>页面/API/导入/执行"]
    end

    T2 & T3 -.->|@pytest.mark.integration| MALL[("demo-mall:5000<br/>可跳过")]
```

| 文件 | 条数 | 依赖 |
|---|---|---|
| `tests/conftest.py` | — | 临时库 app / client / logged_in fixtures |
| `tests/test_assert_engine.py` | 9 | 无（纯内存） |

## 3. 如何实现

### 3.1 测试分层与"金字塔"在本项目的落法

| 层 | 测什么 | 手段 | 数量占比 |
|---|---|---|---|
| 单测（快） | 断言逻辑、请求构造、token 缓存、错误降级 | 内存 Response / monkeypatch | ~70% |
| 端到端（进程内） | 路由+校验+落库+渲染整链路 | Flask test client + 临时库 | ~28% |
| 集成（真环境） | 对真 demo-mall 的真实 HTTP | 真服务 + 探活 skip | ~2%（但含金量高） |

为什么集成占比刻意小：真实服务测试慢、依赖环境、数据有状态（重跑要 reset），价值在"验证接线正确"而不是"验证逻辑分支"——逻辑分支全部下沉到前两层。

### 3.2 conftest：隔离是第一原则

```python
@pytest.fixture()
def app(tmp_path):
    test_config = {
        "DB_PATH": str(tmp_path / "test_platform.db"),   # 每个测试独立临时库
        "SECRET_KEY": "test-secret-key",
        "TESTING": True,
        "EXECUTION_CONCURRENCY": 3,                       # 小并发，顺带暴露竞态
    }
    application = create_app(test_config)
    with application.app_context():
        insert("INSERT INTO users(username, password_hash) VALUES(?,?)",
               ("admin", hash_password("admin123")))
    yield application

@pytest.fixture()
def logged_in(client):
    resp = client.post("/api/login", json={"username": "admin", "password": "admin123"})
    assert resp.get_json()["code"] == 0
    return client
```

三个关键点：
- **每个测试一个新 app + 新 SQLite 文件**（tmp_path 是 pytest 内置的每测试独立目录）——测试之间零共享，顺序无关；
- **test client 不起端口**：`app.test_client()` 在进程内直接调 WSGI，session/cookie 行为与真浏览器一致，测试速度快两个数量级；
- **集成测试的探活**：`_mall_up()` 先 GET /api/health（2 秒超时），不通就 `pytest.skip("demo-mall(5000) 未运行")`——CI 里没起被测系统也不红。

### 3.3 断言引擎单测：mock Response 而不是 mock 整个库

```python
def make_resp(status=200, body=None, raw=None):
    """requests.Response 可以直接塞 _content，无需起服务。"""
    resp = requests.Response()
    resp.status_code = status
    resp._content = (raw.encode("utf-8") if raw is not None
                     else json.dumps(body, ensure_ascii=False).encode("utf-8"))
    resp.headers["Content-Type"] = "application/json"
    return resp

def test_partial_fail_all_items_reported():
    """部分失败：失败的断言不能让后面的断言"没机会跑"——平台版与 pytest 版的核心差异。"""
    resp = make_resp(200, {"code": 1002, "message": "密码错误", "data": None})
    results = assert_engine.check(resp, {
        "status_code": 200, "code": 0,
        "fields": {"$.message": "密码错误", "$.data.token": "abc"}})
    assert [r["passed"] for r in results] == [True, False, True, False]  # 全部执行
```

测试矩阵（9 条）：三层全过 / 部分失败逐条报告 / 状态码失败 / JSONPath 未命中 / 列表下标 / **非 JSON 响应**（网关 HTML 页）/ 空期望 / int-float 宽松相等 / 中文值。每条对应断言引擎的一个真实决策（比如"非 JSON 是被测行为不是崩溃"）。

### 3.4 执行引擎单测：monkeypatch 唯一 HTTP 出口

```python
def fake_send(method, url, **kwargs):
    calls.append({"method": method, "url": url, "json": kwargs.get("json_body"),
                  "headers": kwargs.get("headers")})
    if url.endswith("/api/auth/login"):
        return make_resp(200, {"code": 0, "data": {"token": "tok-123"}})
    return make_resp(200, {"code": 0, "data": {"username": "lemon"}})

monkeypatch.setattr(runner, "_send", fake_send)   # runner._send 是全平台唯一出站口
```

因为 runner 把所有出站请求收口在 `_send` 一个函数（类似参考框架"RestClient 是全框架唯一 HTTP 出口"），单测注入一个 fake 就能覆盖：请求构造（url/params/body 反序列化）、**自动登录恰好一次**（两条用例同账号，login_count==1）、伪造 token 头优先、快照脱敏、expect_code=0 不被吞。唯一不打 mock 的是网络错误测试：对 `http://127.0.0.1:9`（必然拒绝的端口）真实请求，验证"网络错误降级为失败明细、不抛异常"。

模块级 `_token_cache` 是共享状态，autouse fixture 每条测试前后 `clear_token_cache()`——**全局状态必须显式清理**，否则测试顺序一变就随机挂。

### 3.5 Web/API 端到端：test client 的典型用法

```python
def test_execute_single_case_dead_port(self, logged_in):
    """死端口执行：专测错误降级路径（不需要真被测系统）。"""
    pid = _create_project(logged_in, base_url="http://127.0.0.1:9")
    cid = logged_in.post(f"/api/projects/{pid}/cases", json=_case_payload()).get_json()["data"]["id"]
    data = logged_in.post(f"/api/cases/{cid}/execute").get_json()["data"]
    assert data["passed"] == 0 and data["failed"] == 1 and data["status"] == "failed"
    detail = logged_in.get(f"/api/executions/{data['execution_id']}").get_json()["data"]
    assert detail["items"][0]["asserts"][0]["item"] == "网络请求"
```

页面断言同样直出：

### 3.6 集成测试与标记隔离

```python
@pytest.mark.integration
class TestAgainstRealMall:
    def test_execute_batch_concurrent(self, app):
        if not _mall_up():
            pytest.skip("demo-mall(5000) 未运行")
        ...  # 临时库建 3 条用例 → execute_batch → 断言 summary total=3 passed=3 status=done
```

pytest.ini 声明标记后，两种跑法各司其职：

```bash
python -m pytest tests/ -v -m "not integration"   # 35 passed（无外部依赖，随时跑）
python -m pytest tests/ -v                        # 38 passed（起 demo-mall 后全量）
```

## 4. 为什么这样设计（决策复盘）

| 决策 | 选择 | 备选 | 理由 |
|---|---|---|---|
| 隔离 | 每测试独立临时库 + 新 app | 共享开发库/内存库复用 | 顺序无关 + 不污染数据 |
| HTTP mock 点 | monkeypatch runner._send | requests-mock / 本地 mock server | _send 是平台唯一出站口，注入面最小 |
| 网络错误的测法 | 真连死端口 | mock 抛异常 | 覆盖 requests 真实异常类型；localhost 拒绝是毫秒级 |
| 集成测试 | 标记 + 探活 skip | 永远跑 / 单独仓库 | CI 无被测环境也能绿；标记让"全量"与"快速"两种跑法共存 |
| 全局缓存 | autouse fixture 清理 | 测试里手动清 | 人会忘；autouse 是顺序无关的保障 |
| 页面断言 | 稳定 id 存在性 | 断言整段 HTML | HTML 改版不断测试；id 契约同时服务 UI 自动化 |

## 6. 常见坑

1. **测试读了开发库**：conftest 忘传 DB_PATH，测试数据写进 `instance/test_platform.db`——检查方法：跑完测试看开发库的 cases 数有没有变多。
2. **模块级缓存污染**：token 缓存/全局 Session 不清，单测"单独跑过、全量跑挂"；全局可变状态必须有 autouse 清理 fixture。
3. **集成测试依赖数据状态**：断言 `$.data.total: 10` 依赖 demo-mall 种子商品数——所以集成测试跑前要 reset，且测试自身尽量选无状态断言（本文集成用例只断言"执行通过"，不断言商品库存这类会变的数）。
4. **test client 的 302 跟随**：`client.get("/projects")` 未登录会自动跟到 /login 返回 200，断言"重定向"必须 `allow_redirects=False` 或检查 `resp.status_code == 302`。
5. **fixture 作用域用错**：app 用 function 级，若改成 session 级，临时库共享、测试开始互相踩数据；隔离性优先于那点启动速度。

## 7. 面试怎么讲（30 秒 + 3 追问）

**30 秒版本**：
"平台自己有 38 条 pytest，分三层：断言引擎 9 条纯单测，用内存构造的 Response 覆盖三层断言矩阵包括非 JSON 响应；执行引擎 8 条 mock 单测——因为出站请求收口在 _send 一个函数，monkeypatch 一个点就能验证请求构造、token 只登录一次、伪造头优先、网络错误降级；Web/API 用 Flask test client 走端到端，每个测试独立临时库。需要真被测系统的 3 条标了 integration 并做探活 skip，CI 没有被测环境也能全绿。"

**追问 1：为什么 test client 能代表真实请求？**
"test_client 直接调 WSGI 应用，路由/装饰器/JSON 解析/session cookie 全是同一套代码，只有网络栈被替掉——而这正是平台测试不需要的部分。验证'真的能通过 HTTP 访问'这件事，交给部署后的页面可访问性脚本（requests 会话登录拉页面断言 id），两层互补。"

**追问 2：集成测试怎么保证可重复？**
"三条原则：探活 skip 环境不通就跳、断言选确定性数据（种子商品数、固定账号）、测试自己不产生有状态残留（只用查询和登录类用例）。平台的全量用例里有'注册新用户'这种改变数据的正向用例，那是被测行为的一部分，跑之前由调用方负责 reset——测试代码和被测数据的边界要清楚。"

**追问 3：mock 点为什么选 _send 而不是用 requests-mock？**
"因为 runner 刻意把出站请求收口在一个函数（与参考框架'RestClient 是唯一 HTTP 出口'同一思想），monkeypatch 一个符号注入面最小、不引入额外依赖。如果哪天换 httpx 异步，只改 _send 内部实现，全部单测不动——mock 点选在架构边界上，测试才不会被实现细节绑死。"
