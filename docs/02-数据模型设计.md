# test-platform · 文档02 数据模型设计

> 一句话：六张表如何支撑"用例定义"与"执行历史"的彻底分离；JSON 文本列、快照冗余、不设外键——每个"反范式"决定都有明确的交换条件。

## 3. 如何实现

### 3.1 六张表职责与关键字段

```sql
CREATE TABLE IF NOT EXISTS cases (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id    INTEGER NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    name          TEXT    NOT NULL,
    method        TEXT    NOT NULL DEFAULT 'GET',
    path          TEXT    NOT NULL DEFAULT '/',
    headers       TEXT    NOT NULL DEFAULT '',  -- JSON 文本
    params        TEXT    NOT NULL DEFAULT '',  -- JSON 文本：查询串
    body          TEXT    NOT NULL DEFAULT '',  -- JSON 文本：请求体
    auth_user     TEXT    NOT NULL DEFAULT '',  -- 非空 = 执行前自动登录
    auth_pass     TEXT    NOT NULL DEFAULT '',
    expect_status INTEGER,                      -- NULL = 该层不断言
    expect_code   INTEGER,                      -- 0 是合法值！判空用 IS NULL
    expect_fields TEXT    NOT NULL DEFAULT '',  -- JSON 文本 {"$.data.x":"y"}
    created_at ..., updated_at ...
);
```

三个关键点：
- **期望三层各一列**：`expect_status` / `expect_code` / `expect_fields` 与断言三层一一对应，且每层独立可空——"只断业务码不断状态码"用例是合法且常见的；
- **headers/params/body 存 JSON 文本**，空串表示"不带"，读出时 `json.loads`；
- **auth_user/auth_pass 就地存**：执行引擎"自动登录"的数据来源（安全取舍见第 4 节）。

### 3.2 executions 与 execution_items 为什么拆两层

```sql
executions(id, project_id, status, total, passed, failed, error, duration_ms, created_at)
execution_items(id, execution_id, case_id, case_name, passed, status_code, resp_code,
                duration_ms, request_snapshot, response_snapshot, asserts, created_at)
```

一次"一键执行"产生 1 行 executions + N 行 execution_items（N=用例数）。拆两层的理由：

1. **查询模式不同**：列表页只要批次汇总（1 行/批），详情页才要明细（N 行/批）——汇总行让"最近通过率"这类高频查询不碰大表；
2. **口径清晰**：total/passed/failed 落在批次行上是"定稿数字"，避免每次都 `SUM(items)` 且与"并发中途查看"的瞬时值打架；
3. **历史快照语义**：明细行的 `case_name` 是**冗余快照**——用例后来改名，历史报告仍显示执行当时的名字。

对应的"执行历史"表同理：`case_id` **故意不设外键**——用例被删除后，历史明细必须还能完整展示（审计需求），设了 FK + CASCADE 就会把历史一起抹掉。

### 3.3 JSON 文本列的取舍

headers/params/body/expect_fields/asserts/snapshot 都存 JSON 文本：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **JSON 文本列（选它）** | 字段数不定形也能存；整存整取，读写简单；SQLite 原生支持 json 函数 | 不能 SQL 级按字段查询/索引 | 用例体量小、查询总按 id/项目维度，可接受 |
| 拆关系列（如 expect_field_name/expect_field_value 子表） | 可 SQL 过滤"哪些用例断言了某字段" | 表数量翻倍、写路径复杂；这个查询需求 v1 不存在 | 过度设计 |
| 换 PostgreSQL JSONB | 可索引 JSON | 引入数据库安装/迁移成本，违背零依赖目标 | 真需要再换 |

代码侧的约定：**入口归一、出口解析**。写入前 importer.normalize_case 把 dict 统一 `json.dumps(ensure_ascii=False)`；读出后 API 层 `parse_json_text` 解析回对象——前端和模板永远拿到的是对象，不碰原始文本。

### 3.4 db.py 的助手函数

```python
def execute(sql, args=()) -> int:
    """写语句，返回 rowcount，自动提交。"""
    cur = get_db().execute(sql, args)
    get_db().commit()
    return cur.rowcount

def insert(sql, args=()) -> int:
    """INSERT，返回 lastrowid，自动提交。"""
```

为什么 execute/insert 自动 commit 而 demo-mall 是手动 commit：平台的写路径全部收口在这两个函数（十几个调用点），自动提交消灭了"接口返回成功但数据没落库"这类最难排查的坑；代价是没有跨语句事务——平台的写操作都是单语句，这个代价为零。

`get_db()` 用 Flask 的 g 对象：请求内复用一个连接、请求结束 teardown 关闭；`PRAGMA foreign_keys = ON` 必须每个连接都开（SQLite 默认关闭外键，不开则 CASCADE 全部失效——这是 SQLite 最著名的静默坑之一）。

### 3.5 import_logs：第六张表

导入是"批量改变用例集"的动作，必须留痕：

```sql
import_logs(id, project_id, source, imported, skipped, message, created_at)
```

排查"用例怎么凭空多了 51 条"时，这张表能直接回答：什么时候、什么来源、导了几条、跳了几条、为什么跳。

## 4. 为什么这样设计（决策复盘）

| 决策 | 选择 | 备选 | 理由 |
|---|---|---|---|
| executions/items 拆两层 | 两层 | 单表（批号列） | 查询模式不同 + 口径定稿 |
| case_id 不设外键 | 弱关联 | FK + CASCADE | 删用例不能毁执行历史 |
| case_name 冗余进明细 | 快照 | join 查现值 | 历史报告要"当时的名字" |
| 不定形字段 | JSON 文本 | EAV 子表 / JSONB | 查询需求不存在，简单优先 |
| 期望三层 | 三列 | 单个 JSON 列 | 三层是"一等公民"，独立可空、可单列统计 |
| 自增 id 归零 | RESET sqlite_sequence | 保留 | 种子重置后演示 id 确定（截图/文档可复现） |
| 密码字段 | password_hash（pbkdf2 带盐） | 明文/简单哈希 | 见文档03 |

## 6. 常见坑

1. **`expect_code=0` 被当成"没配"**：Python 里 `if expect_code:` 会把 0 判为假——必须 `is not None` / SQL 里 `IS NULL`。tests/test_runner.py 有专门的回归用例。
2. **PRAGMA foreign_keys 忘开**：SQLite 每个连接默认关闭外键，DELETE projects 后 cases 还在，页面出现"幽灵用例"；get_db 里每个连接都要执行一次。
3. **JSON 文本列直接拿去渲染**：模板里显示 `{\"code\": 0}` 乱码——读出侧必须统一 `parse_json_text` 解析，模板保持纯展示。
4. **并发写库 "database is locked"**：本平台规避了（worker 线程不发 SQL，落库在调用线程串行）；如果你把 `get_db()` 拿进线程池，就会撞上 sqlite3 的跨线程限制与锁竞争。
5. **updated_at 忘更新**：UPDATE 语句不带 `updated_at=datetime('now','localtime')`，用例列表看不出谁刚改过——SQLite 没有 ON UPDATE，要手写。

## 7. 面试怎么讲（30 秒 + 3 追问）

**30 秒版本**：
"平台六张表分三组：定义侧 users/projects/cases，执行侧 executions/execution_items，运维侧 import_logs。核心拆分是'用例定义'与'执行历史'彻底分离——执行明细冗余存当时的用例名、case_id 不设外键，保证删用例不毁历史报告。请求体、期望字段这类不定形结构存 JSON 文本，入口归一化、出口统一解析，避免为不存在的查询需求做 EAV 拆表。"

**追问 1：为什么 executions 和 execution_items 拆两层而不是一张大表？**
"查询模式不同：列表页只要每批一行汇总，明细只有详情页才读。拆开后'最近通过率'这类高频查询不碰大表，而且 total/passed 是批次定稿数字，口径不会和'跑一半时 SUM 的瞬时值'打架。"

**追问 2：JSON 文本列不能索引，不怕查不动吗？**
"我的查询全部按 id/项目/批次维度，都是索引列；唯一按内容查 JSON 的场景——'哪些用例断言了某字段'——v1 不存在。数据驱动设计的第一原则是为真实查询建模，不是为假想需求建索引；真需要时升级 PostgreSQL JSONB 或拆子表，入口归一化的设计让这个升级只动 db 一层。"

**追问 3：执行历史为什么保留 case_id 冗余又不设外键？**
"执行记录是'事实'，用例定义是'配置'。事实一旦发生不该随配置消失——用户删了 20 条旧用例后，上个月的批次报告必须还能完整打开。所以明细里冗余 case_name 快照、case_id 弱关联，这是我刻意做的反范式。"
